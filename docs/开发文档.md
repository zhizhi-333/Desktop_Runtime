# 开发文档：STM32F407 智能人机交互系统多任务架构设计

> 本文档阐述基于 FreeRTOS 的多任务协作架构设计理由，涵盖任务划分、优先级分配、任务间通信、共享资源同步保护、异常处理策略，以及"后台操作不阻塞输入响应与界面刷新"要求的具体实现。对应代码位于 `d:\assseement\microcomputer`。

---

## 一、设计目标与问题分析

### 1.1 系统功能清单

本系统是人机交互终端，需同时支撑以下功能：

| 功能域 | 具体功能 | 实时性要求 |
|--------|---------|-----------|
| 输入采集 | 4×4 矩阵键盘扫描、旋转编码器正交解码 | 高（人眼可感知延迟 < 50ms） |
| 界面刷新 | LCD 480×320 局部/全屏重绘、状态栏更新 | 中（30~50ms 内完成一帧） |
| 文件读写 | SD 卡块读写（文件创建/查看/编辑/删除/重命名） | 低（百毫秒级可接受，但不能卡死输入） |
| 音乐播放 | DAC 方波合成、音符按节拍推进 | 中（20ms 节拍精度） |
| 日志记录 | 串口输出 + 环形缓冲持久化 | 低（异步即可） |
| 系统监控 | 堆/栈水位采样、错误计数、健康日志 | 低（1 秒周期） |

### 1.2 单主循环方案的问题

若采用"单任务主循环 + FreeRTOS"方式（即 `while(1){ 扫键 → 刷屏 → 读 SD → 推进音乐 → 记日志 }`），会面临三类严重问题：

**问题 1：SD 卡 I/O 阻塞输入**
SD 卡单块读写耗时可达 10~100ms（SPI 模式 4MHz 时钟下，512 字节 ≈ 1ms 传输 + 数十毫秒等待）。在此期间主循环无法扫描键盘，用户会感到按键"无响应"。

**问题 2：音乐节拍被破坏**
音乐播放需要每 20ms 推进一个音符（切换 DAC 频率）。若主循环正卡在 SD 卡 I/O 上，音符推进会被推迟数百毫秒，旋律听感变调、卡顿。

**问题 3：共享资源数据竞争**
日志缓冲区、系统设置（Flash）、DAC 寄存器会被多个调用路径并发访问。单循环下虽无真并发，但一旦拆成多任务后，若无同步保护，会出现"日志条目交错"、"Flash 擦写被中途打断"等故障。

### 1.3 设计原则

基于上述分析，确立三条设计原则：

1. **输入最优先**：键盘/编码器扫描与 UI 重绘放在最高优先级任务，绝不因后台 I/O 延迟
2. **I/O 异步化**：SD 卡、DAC 等慢速/长周期操作拆到独立任务，通过队列与 UI 任务解耦
3. **资源有锁必锁**：所有跨任务共享的资源用互斥量保护，且带超时兜底防止死锁

### 1.4 设计理念：FreeRTOS 的应用哲学

本项目选择 FreeRTOS 作为操作系统，并非为了"用 RTOS 而用 RTOS"，而是因为单线程主循环（super-loop）架构在面对"输入响应 + 慢速 I/O + 实时音频 + 系统监控"这四类并存需求时存在根本性矛盾。FreeRTOS 提供的**任务调度、队列通信、互斥量同步、软件定时器、钩子函数**等机制，恰好对应这些矛盾的解法。本节阐述本项目如何系统性地运用 FreeRTOS 的核心特性。

#### 1.4.1 为什么要用 RTOS：从 super-loop 到多任务的必然性

传统嵌入式程序的 `while(1){ 扫键→刷屏→读SD→推进音乐→记日志 }` 主循环看似简单，但存在三个无法调和的矛盾：

| 矛盾 | super-loop 的表现 | FreeRTOS 的解法 |
|------|------------------|----------------|
| **慢 I/O vs 输入响应** | SD 卡读写 10~100ms，期间无法扫键 | 拆出 FileTask 独立任务，InputTask 抢占式调度不受影响 |
| **实时音频 vs 阻塞操作** | SD 卡阻塞时音乐节拍停滞 | MusicTask 独立任务，按 20ms 周期被定时器唤醒，与 FileTask 并行 |
| **功能扩展 vs 响应确定性** | 加一个功能就拉长主循环，响应时间不可预测 | 任务相互独立，新增功能不影响其他任务的时序保证 |

**核心理念**：RTOS 把"时间"显式化为调度器管理的资源，每个任务获得确定的 CPU 时间片，时序保证由优先级和抢占机制兜底，而非靠程序员手动在主循环里"挤时间"。

#### 1.4.2 任务划分哲学：按"实时性等级"而非"功能模块"切分

常见的错误做法是按功能模块切任务（"键盘任务"、"显示任务"、"文件任务"…），这会导致任务数爆炸且优先级难以分配。本项目按**实时性等级**划分任务：

```
┌─────────────────────────────────────────────────┐
│ 实时性等级    │ 代表任务        │ 调度策略       │
├─────────────────────────────────────────────────┤
│ 硬实时(<20ms) │ InputTask       │ 固定周期+抢占  │
│ 软实时(20ms)  │ MusicTask       │ 固定周期       │
│ 尽力而为      │ FileTask        │ 事件驱动+阻塞  │
│ 后台辅助      │ LedTask         │ 固定周期       │
│ 监控诊断      │ MonitorTask     │ 固定周期+最低  │
└─────────────────────────────────────────────────┘
```

**划分依据**：
- **InputTask 独立为最高优先级**：人机交互的延迟阈值是 100ms，20ms 扫描周期 + 最高优先级抢占，保证按键响应永远在 20ms 内处理
- **MusicTask 独立而非合并到 InputTask**：音乐节拍是时间驱动的（每 20ms 推进一个音符），若与 UI 共任务，UI 重绘耗时就会影响节拍精度。独立任务后，MusicTask 即使在 FileTask 写 SD 卡期间也能按时唤醒
- **FileTask 用阻塞而非轮询**：SD 卡 I/O 是事件驱动的（用户按 OK 才读文件），用 `xQueueReceive` 阻塞等待请求，无请求时让出 CPU，不占用时间片
- **MonitorTask 最低优先级**：监控是"锦上添花"，绝不能与功能任务抢 CPU。低优先级使它在高负载时自然被挤占，但功能任务不受影响

#### 1.4.3 优先级策略：抢占式 + 时间片轮转的混合调度

FreeRTOS 支持两种调度策略：**抢占式**（高优先级立即抢占低优先级）和**时间片轮转**（同级任务公平分享 CPU）。本项目刻意采用混合策略：

| 优先级 | 任务 | 调度方式 | 理由 |
|--------|------|---------|------|
| 3 | InputTask | 抢占式 | 输入必须立即响应，任何时候都能抢占所有其他任务 |
| 2 | FileTask/MusicTask/LedTask | 时间片轮转 | 同级任务无相互优先关系，1ms 时间片公平分享 |
| 1 | MonitorTask | 抢占式（被抢占） | 最低优先级，所有任务都能抢占它 |
| 0 | Idle | 空闲任务 | FreeRTOS 内核管理，运行空闲钩子 |

**为何同级用时间片轮转而非细分优先级？**
如果把 FileTask 设为 2、MusicTask 设为 3，看似"音乐更实时"，但会导致：
- FileTask 写 SD 卡时被 MusicTask 频繁抢占，SD 卡写操作被打断可能超时
- 优先级反转风险：FileTask 持有 `log_mutex` 时被 MusicTask 抢占，MusicTask 又要写日志，形成死锁

同级时间片轮转让三者公平竞争，1ms 时间片足够 MusicTask 的 20ms 节拍精度，也不会让 SD 卡写操作被打断太久。

#### 1.4.4 任务间通信哲学：队列解耦而非共享变量

FreeRTOS 的队列（Queue）是任务间通信的首选机制，相比裸共享变量有三大优势：

1. **天然同步**：`xQueueSend` 和 `xQueueReceive` 内部带阻塞/唤醒机制，无需额外信号量
2. **数据拷贝而非指针**：队列传递的是数据副本，发送方发送后即可释放缓冲区，不存在"数据被读一半时被改写"的竞态
3. **生产者-消费者解耦**：生产者投递后立即返回，消费者按自己节奏处理，两者时序完全独立

本项目的通信架构：

```
InputTask ──(file_req_queue)──> FileTask
InputTask <──(file_resp_queue)── FileTask
InputTask ──(music_cmd_queue)──> MusicTask
```

**为何用双队列（请求+响应）而非单队列？**
单队列下 FileTask 处理完无法"送回"结果给 InputTask。双队列实现天然的"请求-响应"模式，InputTask 投递请求后立即返回继续扫键，下一帧用 `xQueueReceive(resp, 0)` 非阻塞轮询结果。

**队列长度选择 4 的理由**：
- 过短（1）：连续创建多个文件时第二次请求丢失
- 过长（16）：占用过多 RAM 且堆积请求导致响应延迟累加
- 4 兼顾突发性与内存占用（每个请求约 24 字节，4 个 = 96 字节）

#### 1.4.5 资源同步哲学：互斥量 + 优先级继承

FreeRTOS 的互斥量（Mutex）相比二值信号量（Binary Semaphore）多了**优先级继承**机制，这是防止优先级反转的关键。

**优先级反转场景**（如果用信号量）：
```
时刻 T1: FileTask(优先级2) 获取 log_mutex
时刻 T2: InputTask(优先级3) 要写日志，阻塞等待 log_mutex
时刻 T3: MusicTask(优先级2) 就绪，因与 FileTask 同级而抢占 CPU
        → FileTask 无法运行释放锁 → InputTask 被无限阻塞
```

**互斥量+优先级继承**：
```
时刻 T2: InputTask(优先级3) 等待 log_mutex
        → FileTask 被临时提升到优先级3
        → MusicTask(优先级2) 无法抢占 FileTask
        → FileTask 快速释放锁 → InputTask 立即运行
```

本项目所有跨任务共享资源均用互斥量（而非信号量）：
- `log_mutex`：日志缓冲区
- `settings_mutex`：Flash 设置擦写
- `dac_mutex`：TIM6 启停序列

#### 1.4.6 阻塞式设计的艺术：让任务"睡"而非"忙等"

FreeRTOS 的 `vTaskDelay` / `vTaskDelayUntil` / `xQueueReceive` 在阻塞时会让出 CPU，调度器切换到其他就绪任务。本项目刻意利用这一特性，让任务"大部分时间在睡觉"：

| 任务 | 阻塞方式 | 醒来时机 | CPU 占用率 |
|------|---------|---------|-----------|
| InputTask | `vTaskDelayUntil(20ms)` | 20ms 周期到期 | ~5% |
| FileTask | `xQueueReceive(portMAX_DELAY)` | 收到文件请求 | ~1% |
| MusicTask | `vTaskDelayUntil(20ms)` | 20ms 周期到期 | ~3% |
| LedTask | `vTaskDelay(500)` | 500ms 延时到期 | <0.1% |
| MonitorTask | `vTaskDelayUntil(1000ms)` | 1 秒周期到期 | ~1% |

**关键设计**：FileTask 用 `portMAX_DELAY`（无限阻塞）等待请求，无请求时永远不占用 CPU。这比轮询（`while(!has_request) vTaskDelay(1)`）更高效，且响应更快——请求到达的瞬间，队列会立即唤醒 FileTask，而非等下一次轮询。

**注意**：后来引入看门狗后，`portMAX_DELAY` 改为 1 秒超时，在超时分支喂心跳，详见 1.4.8。

#### 1.4.7 看门狗与心跳机制：双层保护

FreeRTOS 本身不能检测任务卡死（任务死循环时调度器照常运行）。本项目实现"软件心跳 + 硬件看门狗"双层保护：

**第一层：软件心跳检测**（MonitorTask 实现）
```
每个任务每轮循环调用 Monitor_Heartbeat(HB_xxx)，递增自己的心跳计数器
MonitorTask 每 1 秒检查所有任务的心跳计数器：
  - 如果某任务计数器未变化累计 5 秒 → 判定卡死
  - 设置 SYS_ERR_TASK_HANG 标志，停止喂狗
```

**第二层：硬件看门狗**（IWDG）
```
IWDG 独立看门狗，超时 12.5 秒（LSI=32kHz, Prescaler=256, Reload=1562）
MonitorTask 每秒检查心跳健康后喂狗
如果某任务卡死 5 秒，MonitorTask 停止喂狗
再过 12.5 秒，IWDG 硬件复位整个系统
```

**为何用双层而非单层？**
- 仅 IWDG：只能检测"调度器整体卡死"，单个任务死循环时 IWDG 仍可能被盲目喂狗
- 仅软件心跳：心跳检测逻辑本身可能卡死，无法触发复位
- 双层：软件心跳精准定位"哪个任务卡了"，IWDG 提供硬件级兜底确保最终复位

#### 1.4.8 心跳调度的陷阱：阻塞 API 与看门狗的冲突

引入心跳机制后遇到一个隐蔽问题：FileTask 用 `xQueueReceive(queue, portMAX_DELAY)` 无限阻塞等待请求，当无请求时任务永远阻塞，`Monitor_Heartbeat(HB_FILE)` 永远不执行，MonitorTask 误判 FileTask 卡死，触发系统复位。

**解决方式**：将 `portMAX_DELAY` 改为 1 秒超时，超时分支也喂心跳：

```c
if (xQueueReceive(file_req_queue, &req, pdMS_TO_TICKS(1000)) == pdTRUE) {
    /* 处理请求 */
} 
/* 无论是否收到请求，每秒至少执行一次喂心跳 */
Monitor_Heartbeat(HB_FILE);
```

**教训**：在带看门狗的系统中，所有任务的阻塞调用必须有超时退出机制，`portMAX_DELAY` 是危险信号。心跳调用必须覆盖所有执行路径——循环体末尾、所有 continue/return 之前。

#### 1.4.9 钩子函数：栈溢出与堆失败的运行时检测

FreeRTOS 提供两个可由用户实现的钩子函数，本项目利用它们实现运行时异常检测：

**栈溢出钩子**（`vApplicationStackOverflowHook`）：
- 配置 `configCHECK_FOR_STACK_OVERFLOW = 2`（方法 2：栈指针越界检查 + 栈底魔数校验）
- 任务切换时内核自动检查栈指针是否越界、栈底 16 字节魔数是否被破坏
- 触发时设置 `SYS_ERR_STACK` 标志，串口输出 `!!! STACK OVERFLOW in %s !!!`

**堆失败钩子**（`vApplicationMallocFailedHook`）：
- `pvPortMalloc` 返回 NULL 时触发
- 设置 `SYS_ERR_HEAP` 标志，串口输出告警
- 桌面状态栏显示 `ERR:HP`，提示用户内存不足

**为何不直接复位？**
钩子函数只标记错误标志而不立即复位，便于观察"哪个任务栈溢出"、"何时堆耗尽"，为调试保留现场。SYSMONITOR 应用可实时查看 `MinHeap`（历史最小剩余堆）持续监控内存趋势。

#### 1.4.10 空闲任务的利用：CPU 占用率监控

FreeRTOS 在所有任务阻塞时运行空闲任务（Idle Task，优先级 0）。本项目利用空闲钩子实现 CPU 占用率统计：

- 空闲任务运行时累计一个计数器
- MonitorTask 每秒采样，计算"非空闲时间占比"即 CPU 占用率
- 正常运行时 CPU 占用率约 10~15%，若持续 >80% 说明有任务在忙等

**理念**：空闲任务不是"浪费"，而是系统余量的指标。监控空闲占比能提前发现性能瓶颈，避免在高负载下出现任务响应延迟。

#### 1.4.11 启动时序：调度器启动前后的边界处理

FreeRTOS 调度器启动前（`vTaskStartScheduler` 之前），任务未创建、互斥量虽可创建但无法正常工作（`xSemaphoreTake` 行为未定义）。本项目的启动序列精心设计：

```
阶段1: 调度器启动前（main.c）
  - HAL_Init / GPIO / SPI / USART / LCD 初始化
  - LCD_BootScreen 显示启动画面
  - 创建互斥量（xSemaphoreCreateMutex 在调度器启动前可用）
  - Monitor_Start 创建 5 个任务（任务未运行）
  - vTaskStartScheduler ← 调度器启动

阶段2: 调度器启动后（InputTask 中）
  - RTC 初始化（LSE 超时 1 秒）
  - SD 卡初始化（通过 FileTask 异步）
  - 进入登录界面
```

**关键处理**：所有调用互斥量的代码用 `xTaskGetSchedulerState()` 检测调度器状态，未启动时降级为直写（单线程无竞争）：

```c
if (xTaskGetSchedulerState() == taskSCHEDULER_NOT_STARTED || log_mutex == NULL) {
    add_entry_locked(type, text);  /* 直写，无需锁 */
    return;
}
```

**为何 RTC/SD 初始化移到任务内？**
早期版本在 `main.c` 调度器启动前调用 `MX_RTC_Init()`，LSE 超时 5 秒期间无屏幕刷新，用户看到白屏。移到 InputTask 后，即使 LSE 超时也有启动画面和进度提示，且调度器已运行，看门狗能正常喂狗。

#### 1.4.12 小结：FreeRTOS 特性应用清单

| FreeRTOS 特性 | 本项目应用 | 解决的问题 |
|--------------|-----------|-----------|
| 任务（Task） | 5 个任务按实时性等级划分 | 输入/I/O/音频/监控并行 |
| 优先级抢占 | InputTask 最高，MonitorTask 最低 | 输入响应确定性 |
| 时间片轮转 | FileTask/MusicTask/LedTask 同级 | 公平调度避免饥饿 |
| 队列（Queue） | file_req/resp、music_cmd 三条队列 | 任务间异步通信 |
| 互斥量（Mutex） | log/settings/dac 三个互斥量 | 共享资源保护 + 优先级继承 |
| 信号量（Semaphore） | 未直接使用（互斥量已覆盖） | - |
| 软件定时器 | 未使用（任务周期足够） | - |
| 堆管理（heap_4） | 48KB 堆，支持碎片合并 | 动态分配任务栈/队列 |
| 栈溢出检查 | 方法 2（指针+魔数） | 运行时栈越界检测 |
| 空闲钩子 | CPU 占用率统计 | 性能监控 |
| Tick Hook | 未使用 | - |
| 互斥量优先级继承 | 自动启用 | 防止优先级反转 |
| vTaskDelayUntil | InputTask/MusicTask/MonitorTask | 精确周期唤醒 |
| portMAX_DELAY → 超时 | FileTask 1 秒超时 | 兼顾阻塞与心跳 |
| IWDG + 软件心跳 | 双层保护 | 任务卡死检测与系统复位 |

## 二、任务划分表

系统拆分为 5 个任务，均在 `Monitor_Start()` 中创建（[monitor.c#L488-L501](file:///d:/assseement/microcomputer/User/app/monitor.c#L488-L501)）。

| 任务名 | 优先级 | 栈大小(字) | 栈大小(字节) | 周期/触发 | 职责描述 |
|--------|--------|-----------|-------------|----------|---------|
| **InputTask** | 3（最高） | 512 | 2048 | 20ms 周期 | 矩阵键盘+编码器扫描；系统状态机（BOOT/LOGIN/RUNTIME/SCREEN_OFF/LOCKED）；熄屏唤醒判定；应用 `on_run` 分发；UI 局部/全屏重绘 |
| **FileTask** | 2 | 1024 | 4096 | 事件驱动（队列阻塞） | SD 卡初始化；文件块读写；创建/删除/重命名；通过响应队列回传结果 |
| **MusicTask** | 2 | 512 | 2048 | 20ms 周期 | 接收命令队列指令；按节拍推进音符；调用 DAC 切换频率；播放/暂停/停止控制 |
| **LedTask** | 2 | 256 | 1024 | 500ms 周期 | LED 翻转，作为调度器存活的心跳指示 |
| **MonitorTask** | 1（最低） | 1024 | 4096 | 1000ms 周期 | 堆/栈水位采样；最小堆历史记录；串口健康日志输出；错误计数统计 |

**FreeRTOS 关键配置**（[FreeRTOSConfig.h](file:///d:/assseement/microcomputer/Core/Inc/FreeRTOSConfig.h)）：
- `configTOTAL_HEAP_SIZE = 48KB`（heap_4 管理）
- `configMAX_PRIORITIES = 7`（优先级 0~6，0 为空闲任务）
- `configCHECK_FOR_STACK_OVERFLOW = 2`（方法 2：栈指针 + 完整魔数校验）
- `configUSE_MUTEXES = 1`（启用互斥量及优先级继承）
- `configMAX_SYSCALL_INTERRUPT_PRIORITY = 0x50`（高 4 位优先级 = 5，符合 STM32F4 4-bit 抢占优先级）

**栈分配理由**：
- **MonitorTask 1024 字**：调用 `vsnprintf` 格式化串口日志，该函数栈消耗大（约 1~2KB），给足余量
- **FileTask 1024 字**：`FileSys_Read/Write` 内部使用 512 字节块缓冲，叠加 SD 卡 HAL 调用栈帧
- **InputTask 512 字**：UI 重绘调用 `GUI_DrawString` 等函数，栈消耗中等
- **MusicTask 512 字**：仅调用 `Music_Update` 和 DAC 接口，栈消耗较小
- **LedTask 256 字**：最轻量，仅 `HAL_GPIO_TogglePin`

## 三、优先级设计理由

### 3.1 优先级层次

```
优先级 3:  InputTask   ← 最高（输入响应）
优先级 2:  FileTask    ┐
           MusicTask   ├ 同级（后台 I/O，时间片轮转）
           LedTask     ┘
优先级 1:  MonitorTask ← 最低（统计日志）
优先级 0:  Idle        ← FreeRTOS 空闲任务
```

### 3.2 各层选择理由

**InputTask = 3（最高）**

人机交互系统对输入延迟最敏感。心理学研究表明，按键响应延迟超过 100ms 人眼可察觉"卡顿"，超过 200ms 会感到"无反应"。InputTask 以 20ms 周期扫描键盘，优先级最高保证即使 FileTask 正在写 SD 卡，下一次 20ms tick 到来时也能立即抢占，维持按键扫描的实时性。同时 UI 重绘也在 InputTask 内完成，避免"输入已采集但界面不更新"的割裂感。

**FileTask = MusicTask = LedTask = 2（同级）**

三者均为后台 I/O 任务，无硬实时要求：
- FileTask：SD 卡 I/O 耗时不可预测（受卡品牌、块地址影响），但延迟百毫秒级用户可接受
- MusicTask：20ms 节拍精度足够，偶发 10ms 抖动人耳不可辨
- LedTask：500ms 翻转，无精度要求

三者同级，由 FreeRTOS 时间片轮转（Round-Robin）公平调度。每个时间片（默认 1ms）切换一次，确保不会有一个任务长时间独占 CPU。

**MonitorTask = 1（最低）**

监控任务仅做采样和日志打印，无功能影响。设为最低优先级确保它绝不抢占任何功能任务。当系统高负载时，MonitorTask 自然被挤占，日志延迟可接受；而功能任务不会因监控而受阻。

### 3.3 优先级继承的必要性

由于启用了互斥量（`configUSE_MUTEXES=1`），FreeRTOS 会自动实现优先级继承：当高优先级任务（如 InputTask）等待低优先级任务（如 FileTask）持有的互斥量时，FileTask 会被临时提升到 InputTask 的优先级，避免被同级任务（如 MusicTask）抢占而导致优先级反转。这对 `log_mutex` 尤为重要——InputTask 记录输入事件日志时会触发继承。

## 四、通信方式说明

### 4.1 通信通道总览

| 通道 | 类型 | 长度 | 生产者 | 消费者 | 作用 |
|------|------|------|--------|--------|------|
| `file_req_queue` | 消息队列 | 4 | app_file (InputTask) | FileTask | 投递文件操作请求 |
| `file_resp_queue` | 消息队列 | 4 | FileTask | app_file (InputTask) | 回传操作结果 |
| `music_cmd_queue` | 消息队列 | 4 | app_music (InputTask) | MusicTask | 投递播放控制命令 |

### 4.2 文件操作队列设计

**数据结构**（[file_task.h](file:///d:/assseement/microcomputer/User/app/file_task.h)）：

```c
typedef enum {
    FILE_OP_NONE, FILE_OP_INIT, FILE_OP_READ, FILE_OP_WRITE,
    FILE_OP_CREATE, FILE_OP_DELETE, FILE_OP_RENAME,
} file_op_type_t;

typedef struct {
    file_op_type_t op;      /* 操作类型 */
    int            idx;     /* 文件索引 */
    uint8_t       *buf;     /* 读写缓冲区指针 */
    int            len;     /* 数据长度/缓冲区容量 */
    char           name[13];/* 文件名(create/rename) */
} file_req_t;

typedef struct {
    file_op_type_t op;
    int            result;  /* >=0 成功, <0 失败 */
    int            len;     /* read 时实际读取字节数 */
    uint8_t       *buf;     /* 回传 buf 指针 */
} file_resp_t;
```

**为何用双队列（请求+响应）而非单队列？**

单队列方案下，FileTask 处理完请求后无法把结果"送回"InputTask，因为请求队列被 FileTask 持续消费。双队列实现天然的"请求-响应"解耦：
- InputTask 投递请求后立即返回（`xQueueSend` 非阻塞，timeout=0）
- FileTask 处理完后投递响应（`xQueueSend` 阻塞 portMAX_DELAY）
- InputTask 在下一帧用 `FileTask_GetResponse(0)` 非阻塞轮询响应

**为何队列长度为 4？**

- 过短（如 1）：连续创建多个文件时第二次请求丢失
- 过长（如 16）：占用过多 RAM（每个 `file_req_t` 约 24 字节，16 个 = 384 字节），且堆积的请求会导致响应延迟累加
- 4 兼顾突发性与内存占用：正常操作一次只投一个请求，4 足以吸收短时突发

### 4.3 音乐命令队列设计

**数据结构**（[music_task.h](file:///d:/assseement/microcomputer/User/app/music_task.h)）：

```c
typedef enum {
    MUSIC_CMD_NONE, MUSIC_CMD_LOAD, MUSIC_CMD_PLAY,
    MUSIC_CMD_PAUSE, MUSIC_CMD_RESUME, MUSIC_CMD_STOP, MUSIC_CMD_VOLUME,
} music_cmd_type_t;

typedef struct {
    music_cmd_type_t cmd;
    int              param1;  /* 曲目索引/音量值 */
} music_cmd_t;
```

**为何 MusicTask 用 20ms 周期而非纯事件驱动？**

音乐播放本质是时间驱动的——音符按节拍切换，与外部命令无关。若纯事件驱动，FileTask 无命令时任务永久阻塞，音符推进就停了。因此 MusicTask 采用"周期唤醒 + 非阻塞取命令"混合模式：

```c
for (;;) {
    while (xQueueReceive(music_cmd_queue, &cmd, 0) == pdTRUE) {
        /* 处理所有待处理命令 */
    }
    Music_Update();  /* 推进音符 */
    vTaskDelayUntil(&last_wake, pdMS_TO_TICKS(20));
}
```

这样即使无命令，每 20ms 也会醒来推进播放；有命令时立即消费（命令处理是瞬时的，不阻塞节拍）。

### 4.4 app_file 的 FS_WAIT 状态机

为避免 InputTask 阻塞等待 FileTask 响应，app_file 引入 `FS_WAIT` 子状态（[app_file.c](file:///d:/assseement/microcomputer/User/app/app_file.c)）：

```
[LIST] --OK--> 投递 READ 请求 --> [WAIT]
                                    |
                        (每帧非阻塞轮询响应)
                                    |
              收到响应 --> [VIEW] (content_buf 已填充)
```

`run_wait()` 每帧调用 `FileTask_GetResponse(0)`（timeout=0，立即返回），未收到响应就保持 `FS_WAIT` 状态继续等下一帧，InputTask 不会被阻塞。收到响应后才切到 `FS_VIEW` 绘制内容。

## 五、资源保护方式说明

### 5.1 共享资源清单

| 共享资源 | 同步原语 | 位置 | 保护范围 | 加锁时机 | 超时 |
|---------|---------|------|---------|---------|------|
| 日志缓冲区 | `log_mutex` | [log_store.c](file:///d:/assseement/microcomputer/User/app/log_store.c) | `add_entry` / `LogStore_GetCount` / `LogStore_GetEntry` | 写入条目、读取计数/条目前 | 50ms |
| 系统设置 | `settings_mutex` | [settings.c](file:///d:/assseement/microcomputer/User/app/settings.c) | `Settings_Save`（Flash 擦写） | Flash 擦除+写入前 | 100ms |
| DAC/音频输出 | `dac_mutex` | [dac.c](file:///d:/assseement/microcomputer/User/dev/dac.c) | `DAC_Start` / `DAC_Stop` | 启停 TIM6 中断前 | 50ms |
| 文件表 | 隐式串行 | [file_sys.c](file:///d:/assseement/microcomputer/User/app/file_sys.c) | 所有 `FileSys_*` 调用 | 无需锁（仅 FileTask 访问） | - |

### 5.2 为何用互斥量而非临界区（关中断）？

临界区（`taskENTER_CRITICAL`）会完全禁用中断，适合保护极短的操作（几条指令）。但本系统中：

- **Flash 擦写**：STM32F4 Sector 11 擦除约 1~4 秒，写入约数十毫秒。若关中断，所有任务调度停止，InputTask 无法运行，系统"假死"
- **SD 卡 I/O 期间的日志**：FileTask 写 SD 卡时可能触发日志记录，若日志用临界区，会与 FileTask 的 SD 操作互相阻塞

互斥量仅阻塞其他试图获取同一锁的任务，不影响中断和无关任务。Flash 擦写期间，InputTask 仍可正常扫描键盘（只是无法写设置），系统保持响应。

### 5.3 DAC 的特殊处理：volatile + 免锁中断

DAC 的 `volume` 和 `playing` 变量被 TIM6 中断读取，被任务侧写入。中断侧不能用互斥量（中断中不能阻塞），因此采用"volatile 单字节 + 任务侧加锁"的混合策略：

```c
static volatile uint8_t volume = 50;   /* 中断读取,volatile 保证不被优化 */
static volatile int playing = 0;       /* 中断读取 */

/* TIM6 中断回调(免锁) */
void HAL_TIM_PeriodElapsedCallback(TIM_HandleTypeDef *htim) {
    if (playing) {
        uint16_t amp = 2047UL * volume / 100;  /* 直接读 volatile */
        /* ... 设置 DAC 值 ... */
    }
}

/* 任务侧 SetVolume(免锁,单字节写原子) */
void DAC_SetVolume(uint8_t vol) {
    volume = vol;  /* ARM 单字节 store 原子,无需锁 */
}

/* 任务侧 Start/Stop(加锁,保护 TIM6 启停序列) */
void DAC_Start(void) {
    xSemaphoreTake(dac_mutex, pdMS_TO_TICKS(50));
    if (!playing) {
        playing = 1;
        HAL_TIM_Base_Start_IT(&htim6);  /* 启动中断 */
    }
    xSemaphoreGive(dac_mutex);
}
```

**为何 `volume` 单字节写无需锁？** ARM Cortex-M4 的单字节 `STRB` 指令是原子的（32 位总线单周期访问），中断不会读到"半写入"的值。`volatile` 关键字保证编译器不把变量缓存到寄存器，每次都从内存读取。

### 5.4 超时兜底机制

所有 `xSemaphoreTake` 均带超时，避免死锁时任务永久挂起：

```c
if (xSemaphoreTake(log_mutex, pdMS_TO_TICKS(50)) == pdTRUE) {
    /* 临界区 */
    xSemaphoreGive(log_mutex);
} else {
    /* 超时:丢弃本次日志,避免阻塞 InputTask */
}
```

超时后的降级策略：
- `log_mutex` 超时：丢弃本次日志条目（日志可丢，输入不可丢）
- `settings_mutex` 超时：返回 -1，设置暂不保存（下次再试）
- `dac_mutex` 超时：放弃本次 Start/Stop（音乐偶发故障可接受）

### 5.5 调度器未启动时的处理

系统启动早期（`main.c` 中调度器启动前）可能调用日志/设置/DAC。此时互斥量虽已创建但调度器未运行，`xSemaphoreTake` 会失败。代码用 `xTaskGetSchedulerState()` 检测并降级为直写：

```c
if (xTaskGetSchedulerState() == taskSCHEDULER_NOT_STARTED || log_mutex == NULL) {
    add_entry_locked(type, text);  /* 直写,无需锁 */
    return;
}
```

## 六、异常处理策略

### 6.1 异常场景与处理矩阵

| 异常场景 | 检测方式 | 处理策略 | 用户可见现象 |
|---------|---------|---------|-------------|
| **栈溢出** | `configCHECK_FOR_STACK_OVERFLOW=2`（栈指针越界 + 魔数校验） | `vApplicationStackOverflowHook` 设置 `SYS_ERR_STACK` 标志，串口输出告警 | 桌面状态栏显示 `ERR:STK`（红色） |
| **堆分配失败** | `pvPortMalloc` 返回 NULL | `vApplicationMallocFailedHook` 设置 `SYS_ERR_HEAP` 标志，串口输出告警 | 桌面状态栏显示 `ERR:HP`（红色） |
| **SD 卡缺失/故障** | `FileSys_Init` 返回 -1 | FileTask 回传 `result<0`；app_file 显示 `[NO SD!]`；桌面设置 `SYS_ERR_SD` | 桌面状态栏显示 `ERR:SD`；FILE 应用无法操作 |
| **队列满（请求投递失败）** | `xQueueSend` 返回 errQUEUE_FULL | `FileTask_Request` 返回 0；app_file 显示 `BUSY!` | FILE 应用提示 BUSY，稍后重试 |
| **文件数满** | `FileSys_GetCount() >= FS_MAX_FILES(16)` | app_file 显示 `FULL!` | FILE 应用提示 FULL，无法新建 |
| **重名文件** | `FileSys_NameExists` 返回 1 | `FileSys_Create` 返回 -2；app_file 提示重名 | RENAME 界面显示错误 |
| **RTC 首次上电** | `HAL_RTC_GetFlag(RTC_FLAG_INITS)==RESET` | 设置 `SYS_ERR_RTC`；时间显示 00:00:00 | 桌面状态栏显示 `ERR:RTC`；SETTIME 应用清除 |
| **输入设备断开** | PE6 ID 脚电平=高 | 设置 `SYS_ERR_INPUT`；桌面显示未连接 | 桌面状态栏显示 `ERR:INP` |
| **高频输入抖动** | 20ms 周期去抖 | `Monitor_IncDroppedEvent` 计数 | SYSMONITOR 显示 Dropped 计数 |

### 6.2 栈溢出钩子实现

```c
void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName) {
    sys_err_flags |= SYS_ERR_STACK;
    Log_Printf("!!! STACK OVERFLOW in %s !!!\r\n", pcTaskName);
    /* 不复位,继续运行但标记错误,便于观察 */
}
```

方法 2（`configCHECK_FOR_STACK_OVERFLOW=2`）在任务切换时同时检查：
1. 栈指针是否落入有效栈区域
2. 栈底 16 字节魔数是否被破坏

### 6.3 堆失败钩子实现

```c
void vApplicationMallocFailedHook(void) {
    sys_err_flags |= SYS_ERR_HEAP;
    Log_Printf("!!! MALLOC FAILED !!!\r\n");
}
```

48KB 堆分配给 5 个任务栈（约 12KB）+ 队列/互斥量（约 1KB）+ 应用缓冲（约 2KB），剩余约 33KB 自由堆。`xPortGetMinimumEverFreeHeapSize()` 持续跟踪历史最低值，SYSMONITOR 实时显示。

### 6.4 SD 卡故障的优雅降级

SD 卡故障不影响系统其他功能：
- **桌面**：正常显示，状态栏标红 `ERR:SD`
- **MUSIC 应用**：正常播放（音乐数据在 Flash 中）
- **DRAW 应用**：正常绘图
- **FILE 应用**：进入后显示 `[NO SD!]`，无法创建/读取，但可退出
- **日志**：串口日志正常输出，仅 SD 持久化失败

## 七、"后台不阻塞输入"实现说明

### 7.1 对应关系矩阵

| 要求 | 实现方式 | 验证方法 |
|------|---------|---------|
| 后台操作不长期阻塞输入响应 | FileTask/MusicTask 独立任务 + 队列通信 | FILE 应用读文件时按方向键，光标立即响应 |
| 后台操作不长期阻塞界面刷新 | app_file 用 FS_WAIT 非阻塞轮询，InputTask 20ms 周期保活 | 音乐播放时切换曲目，进度条流畅更新 |
| 屏幕共享资源同步 | LCD 操作仅在 InputTask 调用，天然无竞争 | - |
| 系统配置共享资源同步 | `settings_mutex` 保护 Flash 擦写 | 并发改设置不冲突 |
| 日志缓冲区共享资源同步 | `log_mutex` 保护条目读写 | 日志无交错乱序 |
| 音频输出共享资源同步 | `dac_mutex` 保护 TIM6 启停；volatile 免锁读音量 | 音乐切换无杂音 |

### 7.2 关键代码路径：文件读取不阻塞输入

**传统同步方式（已废弃）**：
```c
/* 错误做法:InputTask 直接调 FileSys_Read,阻塞 100ms */
FileSys_Read(idx, buf, 512);  /* 卡在这里 */
draw_view();                   /* 100ms 后才画 */
```

**异步方式（当前实现）**：
```c
/* app_file.c - run_list() */
file_req_t req = { .op=FILE_OP_READ, .idx=sel_idx, .buf=content_buf, .len=512 };
FileTask_Request(&req, 0);     /* 非阻塞投递,立即返回 */
fs_state = FS_WAIT;            /* 切到等待状态 */

/* app_file.c - run_wait() 每帧调用 */
if (!FileTask_GetResponse(&resp, 0)) return;  /* 未完成,立即返回 */
content_len = resp.result;
fs_state = FS_VIEW;            /* 完成,切到查看状态 */
```

**时序对比**（读取 512 字节文件）：

| 时刻 | 同步方式 | 异步方式 |
|------|---------|---------|
| 0ms | 调用 FileSys_Read | 投递请求，切 FS_WAIT |
| 5ms | 仍在 SD 卡 SPI 传输 | InputTask 扫键，用户按键立即响应 |
| 20ms | 仍在等待 SD 卡就绪 | InputTask 刷新 UI，显示"加载中" |
| 50ms | FileSys_Read 返回 | FileTask 完成读取，投递响应 |
| 55ms | draw_view() 画内容 | InputTask 取到响应，draw_view() 画内容 |

异步方式下，用户在 0~50ms 等待期间可正常按键、其他应用可正常刷新。

### 7.3 关键代码路径：音乐后台播放不阻塞输入

**app_music 投递命令后立即返回**：
```c
/* 按下 OK 键 */
MusicTask_SendCmd(MUSIC_CMD_LOAD, sel_track, 0);  /* 非阻塞 */
MusicTask_SendCmd(MUSIC_CMD_PLAY, 0, 0);           /* 非阻塞 */
/* 立即返回,InputTask 继续扫键 */
```

**MusicTask 后台推进**：
```c
/* MusicTask 每 20ms 唤醒 */
Music_Update();  /* 推进音符,切换 DAC 频率 */
```

用户在音乐播放期间按方向键选曲、按编码器调音量，InputTask 立即响应，音乐不中断。

## 九、启动时序与初始化位置

### 9.1 为何 RTC/SD 初始化移至任务内？

早期版本在 `main.c` 中调度器启动前调用 `MX_RTC_Init()` 和 `FileSys_Init()`，导致白屏故障：
- LSE 晶振起振超时默认 5000ms，期间无调度器、无屏幕刷新
- SD 卡若无卡，`FileSys_Init` 阻塞等待数百毫秒

**修复后启动时序**：

```
main.c:
  HAL_Init()
  MX_GPIO_Init() / MX_SPI_Init() / MX_USART3_Init() / ...
  LCD_Init()              ← 用 LCD_DelayMs(非 SysTick)
  LCD_BootScreen()        ← 显示 2 秒启动画面(进度条)
  Monitor_Start()         ← 创建 5 个任务
  vTaskStartScheduler()   ← 启动调度器

InputTask(调度器启动后):
  RTC_Init()              ← LSE 超时 1000ms,失败设 SYS_ERR_RTC
  显示 "Loading RTC..."
  显示 "Loading SD..."
  (SD 初始化由 FileTask 异步完成)

FileTask(异步):
  FileSys_Init()          ← SD 卡初始化,失败回传 result<0
```

### 9.2 LSE 超时调整

[stm32f4xx_hal_conf.h](file:///d:/assseement/microcomputer/Core/Inc/stm32f4xx_hal_conf.h) 中：
```c
#define LSE_STARTUP_TIMEOUT   1000U   /* 原 5000U,缩短避免阻塞 */
```

LSE 正常起振约 200~500ms，1000ms 超时足够；失败则回退 LSI（精度较低但可用）。

## 十、关键难点与解决方案

### 难点 1：SD 卡 I/O 与输入响应的冲突

**影响**：SD 卡单块读写 10~100ms，期间若在 InputTask 内同步执行，用户按键无响应超过 100ms，体验恶劣。

**解决**：拆分 FileTask，通过双队列异步通信。InputTask 投递请求后立即返回，FS_WAIT 状态每帧非阻塞轮询响应。代价是 app_file 状态机增加一个状态，但换来了输入零阻塞。

### 难点 2：DAC 中断与任务侧的竞态

**影响**：TIM6 中断读取 `volume`/`playing`，任务侧写入。若用互斥量，中断中不能阻塞；若不加保护，可能出现"任务正在改 playing 时中断读到中间态"。

**解决**：`volatile` + 单字节原子写。`volume`（uint8_t）和 `playing`（int，但实际 0/1）在 ARM 上单字节/单字 store 原子，中断读到旧值或新值均安全。`volatile` 防止编译器优化。仅 TIM6 启停序列（涉及多个寄存器）用 `dac_mutex` 保护。

### 难点 3：启动早期互斥量不可用

**影响**：`main.c` 中调度器未启动时调用 `Log_Printf`，此时 `log_mutex` 虽已创建但 `xSemaphoreTake` 行为未定义。

**解决**：`xTaskGetSchedulerState()` 检测，未启动时直写（单线程无竞争）：

```c
if (xTaskGetSchedulerState() == taskSCHEDULER_NOT_STARTED || log_mutex == NULL) {
    add_entry_locked(type, text);
    return;
}
```

### 难点 4：LSE 超时导致白屏

**影响**：`main.c` 中 `MX_RTC_Init()` 在调度器启动前调用，LSE 超时 5000ms 期间无屏幕刷新，用户看到白屏以为死机。

**解决**：两步修复——LSE 超时改 1000ms；RTC 初始化移至 InputTask（调度器启动后），即使超时也有启动画面和进度提示。

## 总结

本系统通过 5 任务的合理划分，实现了"输入最优先、I/O 异步化、监控最低优先"的多任务协作架构。文件操作和音乐播放通过队列与 UI 任务解耦，确保后台 I/O 不阻塞输入响应。日志、设置、DAC 三类共享资源用互斥量保护，并配合超时兜底和优先级继承防止死锁。栈溢出、堆失败、SD 卡故障、队列满等异常均有对应的降级策略，保证系统在故障下仍可运行。SYSMONITOR 应用可视化栈水位、队列水位、错误计数，为架构有效性提供可观测的验证手段。
