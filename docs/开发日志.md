## 一、编译与构建类问题

### 1.1 HAL 模块未启用导致 Undefined Symbol

**现象**：在实现看门狗（IWDG）功能时，链接器报错：
```
Undefined symbol HAL_IWDG_Init (referred from monitor.o)
Undefined symbol HAL_IWDG_Refresh (referred from monitor.o)
```

**排查过程**：
1. 起初以为是头文件未包含，检查 `monitor.c` 已有 `#include "stm32f4xx_hal.h"`
2. 进一步检查 `stm32f4xx_hal_conf.h`，发现 `#define HAL_IWDG_MODULE_ENABLED` 被注释掉
3. STM32CubeMX 生成代码时，如果 CubeMX 里没勾选 IWDG，对应的 HAL 模块默认是注释状态

**解决方式**：
- 在 `Core/Inc/stm32f4xx_hal_conf.h` 中取消注释 `#define HAL_IWDG_MODULE_ENABLED`
- 将 `stm32f4xx_hal_iwdg.c` 添加到 Keil 工程的编译组中
- 同样的问题在 DAC、RTC 模块上也遇到过，解决方式相同

**教训**：STM32 HAL 库采用模块化设计，每个外设的驱动文件需要两步启用——配置宏 + 添加源文件。新增外设时必须同时检查这两处。

### 1.2 ARMCLANG (AC6) 与 ARMCC (AC5) 汇编语法不兼容

**现象**：从 Keil AC5 编译器切换到 AC6 (ARMCLANG) 后，FreeRTOS 移植层汇编代码报语法错误，例如 `__asm void` 语法不被识别。

**排查过程**：
1. 查阅 ARMCLANG 文档，发现 AC6 基于 LLVM/Clang，对内联汇编语法要求更严格
2. AC5 的 `__asm void` 写法是 ARMCC 私有扩展，AC6 不支持
3. 需要改为 `__attribute__((naked))` 标准 GCC 语法

**解决方式**：将 FreeRTOS `port.c` 中的汇编函数从 ARMCC 语法转换为 GCC 语法：
```c
// AC5 写法（旧）
__asm void PendSV_Handler(void) { ... }

// AC6 写法（新）
__attribute__((naked)) void PendSV_Handler(void) { __asm volatile("..."); }
```

**教训**：编译器升级时，汇编层面的代码最容易出问题。FreeRTOS 官方推荐针对 Cortex-M4F 使用 `ARM_CM4F` 移植层（而非 `ARM_CM3`），后者不支持 FPU。

---

### 1.3 .uvprojx 源文件路径大小写不一致

**现象**：在 Windows 上能编译，但移到 Linux（或 CI 系统）后报 "Cannot open source input file"。

**排查过程**：
1. 对比 `.uvprojx` 文件中的路径，发现混用了 `../User/` 和 `../user/`
2. Windows 文件系统不区分大小写，所以能编译；Linux 区分大小写，找不到文件
3. 项目目录实际名称是 `User`（首字母大写）

**解决方式**：统一 `.uvprojx` 中所有源文件路径为 `../User/`（首字母大写），提交修复 commit `3b6d5ff`。

**教训**：跨平台项目必须保持路径大小写一致，即使在 Windows 上开发也要按 Linux 规范来。

---

### 1.4 隐式函数声明与未定义标识符

**现象**：编译时出现大量 C99 警告 `implicit declaration of function 'Log_Printf'`，以及 `undeclared identifier 'e_ecsw'` 错误。

**排查过程**：
1. `Log_Printf` 声明在 `usart.h`，但 `monitor.c` 没有包含该头文件
2. `e_ecsw` 是之前用于编码器开关事件检测的变量，重构时删除了变量定义但漏改了引用处

**解决方式**：
- 在 `monitor.c` 添加 `#include "usart.h"`
- 在 `app_draw.c` 的输入事件检测中移除 `e_ecsw`，改为 `if (e_up || e_down || e_left || e_right || e_ok)`

**教训**：重构时容易遗漏引用清理。建议使用 IDE 的"查找引用"功能确保删除的变量/函数没有残留调用。

### 1.5 未定义颜色标识符

**现象**：编译报错 `undeclared identifier 'CLR_HINT'`。

**排查过程**：`gui.h` 中定义的颜色表里没有 `CLR_HINT`，但 `app_settings.c` 直接使用了它。

**解决方式**：将 `CLR_HINT` 替换为已定义的 `GRAY`，并在 `app_settings.c` 顶部添加 `#define CLR_HINT GRAY` 作为别名。

**教训**：颜色常量应集中定义在一个头文件中，避免各模块自行起名导致冲突。

## 二、任务调度与心跳检测类问题

### 2.1 FileTask 心跳不更新导致看门狗误判

**现象**：系统运行约 12.5 秒后自动复位，串口日志显示 `[WDT] !!! task FileTask hang detected`。

**排查过程**：
1. 查看 `file_task.c`，发现主循环用 `xQueueReceive(file_req_queue, &req, portMAX_DELAY)` 无限等待
2. 当没有文件请求时，任务一直阻塞在 `xQueueReceive` 上，后续的 `Monitor_Heartbeat(HB_FILE)` 永远不会执行
3. MonitorTask 每 1 秒检查所有任务心跳，发现 FileTask 超过 5 秒未更新，判定卡死
4. MonitorTask 停止喂狗，IWDG 在 12.5 秒后触发复位

**解决方式**：将 `xQueueReceive` 的超时从 `portMAX_DELAY` 改为 `pdMS_TO_TICKS(1000)`（1 秒），并在超时分支中调用 `Monitor_Heartbeat(HB_FILE)`：
```c
if (xQueueReceive(file_req_queue, &req, pdMS_TO_TICKS(1000)) == pdTRUE) {
    // 处理文件请求
    ...
}
// 无论是否收到请求，都喂心跳
Monitor_Heartbeat(HB_FILE);
```

**教训**：任务心跳必须放在所有可能的执行路径上，或者确保阻塞调用有超时退出机制。`portMAX_DELAY` 在带看门狗的系统中是危险信号。

---

### 2.2 MusicTask 心跳缺失

**现象**：播放音乐时看门狗偶尔触发复位，日志显示 MusicTask 心跳停滞。

**排查过程**：
1. `music_task.c` 的主循环周期是 20ms，但循环体内没有 `Monitor_Heartbeat(HB_MUSIC)` 调用
2. 音乐播放时任务确实在运行（DAC 有输出），但心跳计数器没递增

**解决方式**：在 `MusicTask` 的 20ms 循环中、`Music_Update()` 调用之后添加 `Monitor_Heartbeat(HB_MUSIC)`。

**教训**：心跳调用位置要遵循"所有路径覆盖"原则，最安全的方式是放在循环体末尾、所有 continue/return 之前。

---

### 2.3 懒初始化互斥量导致递归死锁

**现象**：系统启动后偶发性卡死，调试器显示卡在 `vTaskSwitchContext`。

**排查过程**：
1. 检查发现 DAC 驱动的 `dac_mutex` 在第一次使用时才创建（懒初始化）
2. 如果第一次调用发生在中断上下文（TIM6 中断），`xSemaphoreCreateMutex` 会触发任务切换
3. 在中断中触发任务切换会导致调度器状态混乱，形成递归死锁

**解决方式**：在 `DAC_Init()` 中（调度器启动前）提前创建互斥量：
```c
void DAC_Init(void) {
    if (dac_mutex == NULL)
        dac_mutex = xSemaphoreCreateMutex();
    ...
}
```

**教训**：FreeRTOS 的 API 在中断上下文中只能调用带 `FromISR` 后缀的版本。互斥量创建必须在任务上下文或调度器启动前完成。

---

### 2.4 熄屏功能丢失，自动重启

**现象**：用户反馈"熄屏功能没有了，一阵时间没指令就变成自动重启"。

**排查过程**：
1. 检查 `monitor.c` 的 `InputTask`，熄屏逻辑还在，但看门狗超时复位会打断熄屏
2. 根因是看门狗心跳检测过于严格：某个任务心跳停滞 5 秒就停止喂狗
3. 熄屏状态下用户无操作，如果此时某个任务恰好阻塞过久，就会触发误复位

**解决方式**：
- 调整心跳检测策略，区分"真卡死"和"正常阻塞"
- 确保所有任务的心跳在合理位置更新（见 2.1、2.2）
- 熄屏状态下 MonitorTask 仍然正常运行并喂狗

**教训**：看门狗的灵敏度要与任务实际行为匹配。引入看门狗后必须全面检查所有任务的阻塞点，确保不会误判。

## 三、硬件初始化时序类问题

### 3.1 RTC 初始化在调度器启动前导致白屏

**现象**：上电后屏幕一直白屏，串口无输出，等待 30 秒以上才勉强启动。

**排查过程**：
1. 在 `main.c` 的 `main()` 函数中发现 RTC 初始化在 FreeRTOS 调度器启动之前
2. RTC 依赖 LSE（32.768kHz 外部晶振），LSE 启动时间不确定
3. `stm32f4xx_hal_conf.h` 中 `LSE_STARTUP_TIMEOUT` 配置为 5000ms
4. 如果 LSE 晶振启动慢，`HAL_RTC_Init` 会阻塞最多 5 秒，期间调度器未启动，看门狗可能已超时

**解决方式**：
1. 将 `LSE_STARTUP_TIMEOUT` 从 5000ms 改为 1000ms
2. 将 RTC 初始化从 `main.c` 移到 `InputTask` 中（调度器启动后）
3. SD 卡初始化同样移到任务上下文中，通过 FileTask 异步执行

**教训**：调度器启动前的代码必须避免长阻塞。所有依赖外部硬件（晶振、SD 卡）的初始化都应放到任务中执行，保证看门狗能正常喂狗。

---

### 3.2 LCD 初始化依赖 SysTick 导致启动失败

**现象**：LCD 初始化时调用 `HAL_Delay`，但此时 SysTick 尚未配置完成，导致阻塞。

**解决方式**：实现 `LCD_DelayMs` 使用简单的循环计数延时，不依赖 SysTick，确保在调度器启动前可用。

**教训**：`HAL_Delay` 依赖 SysTick 中断，在 SysTick 未初始化或中断被屏蔽时会死等。启动阶段应使用独立延时实现。

## 四、UI 交互与按键冲突类问题

### 4.1 绘图应用编码器按压功能冲突

**现象**：编码器按压原本用于清空画布，新增最小化功能后两者冲突。

**排查过程**：
1. 用户要求"编码器按压 = 最小化应用"
2. 但绘图应用原本用编码器按压清空画布
3. 两个功能映射到同一个按键，无法区分

**解决方式**：重新分配按键语义：
- 编码器按压 → 最小化应用（统一全局行为）
- OK 长按（≥1秒）→ 清空画布（替代原编码器按压）
- OK 短按 → 切换落笔/抬笔（保持原功能）

实现 OK 长按检测：
```c
if (key->ok && !prev_key.ok) {
    ok_press_tick = xTaskGetTickCount();
    ok_long_triggered = 0;
}
if (key->ok && !ok_long_triggered) {
    if ((xTaskGetTickCount() - ok_press_tick) >= pdMS_TO_TICKS(1000)) {
        // 触发清空
        ok_long_triggered = 1;
    }
}
if (!key->ok && prev_key.ok && !ok_long_triggered) {
    // 短按：切换落笔/抬笔
    pen_down = !pen_down;
}
```

**教训**：按键资源有限时，长按/短按是扩展按键功能的有效手段。但要注意长按触发后设置标志位，防止松开时又触发短按。

---

### 4.2 绘图应用无操作退出仍弹保存框

**现象**：用户反馈"进去后什么都没画就退出，还弹出要不要保存的确认框"。

**排查过程**：
1. 原逻辑是退出时一律弹保存确认框
2. 但如果用户没做任何操作，保存无意义，反而打扰用户

**解决方式**：引入 `draw_dirty` 标志：
- 进入应用时 `draw_dirty = 0`
- 仅在实际画线或清空画布时 `draw_dirty = 1`
- 退出时检查 `draw_dirty`，为 0 则直接退出不弹框

```c
if (e_back) {
    if (!draw_dirty) {
        need_save = 0;
        AppManager_GotoDesktop();
        return;
    }
    draw_state = DRAW_CONFIRM;
    ...
}
```

**教训**：UI 交互要以用户实际行为为依据，避免无意义的打断。状态标志位是跟踪用户操作的有效手段。

---

### 4.3 光标移动残影问题

**现象**：移动十字光标时，路径上残留之前的图形，形成"残影"。

**排查过程**：
1. 原逻辑是先画新光标，再擦旧光标
2. 但擦旧光标时会误擦掉光标下方的内容
3. 重绘顺序错误导致视觉残留

**解决方式**：调整重绘顺序：先填充背景擦除旧光标位置，再重绘该位置的元素，最后画新光标。

**教训**：GUI 重绘顺序很重要，"先擦后画"是避免残影的基本原则。

## 五、存储与数据一致性类问题

### 5.1 掉电导致设置数据损坏

**现象**：掉电时如果正在写 Flash，下次启动读取到的数据是损坏的，导致系统设置异常。

**排查过程**：
1. Flash 写入不是原子操作，掉电时可能写了一半
2. 原代码没有校验机制，直接使用读取的数据

**解决方式**：引入 CRC32 校验：
- 保存设置时：写入数据 + 计算 CRC32 一起存入 Flash
- 加载设置时：读取数据 + CRC32，校验不匹配则恢复默认值
- 串口日志提示：`[SET] CRC mismatch! flash data corrupted`

同样对 SD 卡文件表也加了 CRC32 保护。

**教训**：非易失性存储必须考虑掉电一致性。CRC 校验是简单有效的方案，更高级的可以用双区备份 + 写入序号。

## 六、应用架构类问题

### 6.1 应用最小化与后台播放

**现象**：用户要求"音乐最小化后继续播放，其他应用最小化后冻结"。

**排查过程**：
1. 需要区分"最小化"（挂起保留状态）和"关闭"（彻底退出）
2. 音乐任务 `MusicTask` 是独立任务，与应用 UI 解耦
3. 其他应用（绘图、文件等）是事件驱动的，没有独立后台任务

**解决方式**：
- 设计 `on_pause`/`on_start` 回调，最小化时调用 `on_pause` 保存状态
- 音乐应用最小化时 UI 挂起，但 `MusicTask` 继续运行
- 桌面任务栏显示最小化应用图标，点击恢复

**教训**：UI 与业务逻辑解耦是良好架构的关键。音乐后台播放能实现，正是因为播放逻辑在独立任务中，不依赖 UI 任务。

---

### 6.2 任务栏与桌面布局

**现象**：加任务栏后，应用可用区域从 320 变成 300，布局受影响。

**解决方式**：任务栏只在桌面显示，应用全屏运行时不显示任务栏。这样应用布局不用改，最小化后回桌面才能看到任务栏。

**教训**：UI 改动要考虑对现有布局的影响，最小化侵入性。

## 七、硬件排障类问题

### 7.1 PAM8403 功放无声

**现象**：代码确认正常（MONITOR 中 ISR 计数在增长，串口有 `[DAC] DAC_Start` 日志），但扬声器无声。

**排查过程**：
1. **确认软件侧**：DAC 初始化日志正常，TIM6 中断在运行（ISR 计数递增）
2. **测量 PA4 电压**：静音时应为 1.65V（DAC 中点），播放时应抖动
3. **检查供电**：PAM8403 需要 5V，不能用 3.3V（功率不足）
4. **检查共地**：STM32 GND 必须与 PAM8403 GND 相连
5. **检查扬声器接法**：PAM8403 是 BTL 差分输出，扬声器必须接 +OUT 和 −OUT，不能单端接 GND
6. **检查 MUTE 引脚**：必须悬空或接 VDD，接 GND 会静音

**关键发现**：PAM8403 成品模块已集成输入耦合电容（1µF）和 VEREF 偏置电路，PA4 可直接连模块输入，无需外加电容。

**BTL 单端接法的危害**：PAM8403 的两个输出端都是主动驱动的半桥，如果把 -OUT 接地，当半桥 B 上管导通时会形成 VDD→MOS管→GND 的低阻通路，瞬间烧毁芯片。

**解决方式**：按检查清单逐项排查（详见操作指南第 14 章）。

**教训**：硬件排障要从软件到硬件逐层排查。先用 MONITOR 确认软件正常，再用万用表测电压，最后检查接线。不要一开始就怀疑代码。

---

### 7.2 TaskState 显示状态理解

**现象**：MONITOR 应用中 `TaskState` 显示 `BBRBB`，用户疑问哪个是 MusicTask。

**排查过程**：
1. `TaskState` 是 5 个字符，从左到右对应 MonitorTask、LedTask、InputTask、FileTask、MusicTask
2. `R` = Running（运行中），`B` = Blocked（阻塞），`r` = Ready（就绪）
3. FreeRTOS 同一时刻只有一个任务处于 `R`，其他都是 `B` 或 `r`
4. 用户看到 `....R` 变成 `....B`，是因为音乐刚好播放完，MusicTask 回到阻塞态等待命令

**教训**：实时系统的任务状态是动态的，查看 MONITOR 时看到的状态只是某一瞬间的快照。播放中的 MusicTask 是 `R`，播放结束变 `B`。

## 八、版本控制类问题

### 8.1 CRLF/LF 行尾问题

**现象**：`git status` 显示多个文件被修改，但 `git diff` 看不到实际内容变化，只有行尾警告。

**排查过程**：
1. Windows 使用 CRLF（\r\n），Git 默认使用 LF（\n）
2. `core.autocrlf` 配置导致文件签出时转为 CRLF，提交时转回 LF
3. 如果文件原本是 LF，被编辑器保存为 CRLF，就会产生"假修改"

**解决方式**：
- 用 `git diff --ignore-cr-at-eol` 确认是否只有行尾变化
- 对只有行尾变化的文件执行 `git checkout -- <file>` 还原
- 提交时只 add 真正有内容改动的文件

**教训**：跨平台开发要统一行尾规范。建议在仓库根目录添加 `.gitattributes` 文件指定 `* text=auto`。

## 十、进阶功能开发（2026-08-20）

本章记录实施方案 B 部分列出的 4 项进阶功能的开发过程。考虑到这些功能依赖硬件/工具难以直观验证（如 Stop 模式需万用表测电流、OTA 需外部镜像源），开发策略是**代码层面完整闭环，验证依赖条件具备时再做**。

### 10.1 存储一致性 Flash+SD 双 CRC（确认已完整）

**现象**：实施方案 B.1 提到"Flash 设置 + SD 文件表都要 CRC 校验防掉电损坏"。前期代码已部分实现，需确认是否覆盖完整。

**排查分析**：通读 `settings.c` 和 `file_sys.c` 两个存储模块：
- `settings.c` 用 Flash Sector 11（0x080E0000）单槽存配置：写前 `settings_compute_crc()` 计算 magic~screen_timeout 字段 CRC32 填入；读后比对 magic + CRC，损坏则 `Log_Printf("[SET] CRC mismatch!")` 并恢复默认值；范围 `clamp` 防止数值越界
- `file_sys.c` 文件表 + 块 17 校验块：`save_table` 写表后 `save_table_crc()` 写 magic+CRC32 到 Block 17；`verify_table_crc` 比对支持"匹配/无 CRC/不匹配"三种状态，不匹配时 `table_crc_corrupted` 置位由 `check_table_init` 清理异常条目再重写

**解决方式**：双 CRC 已完整闭环，无需补充。结论：**已实现**。

**教训**：审查现有实现要先通读再判断"是否需要做" vs "已经做了"。不要重复造轮子，更不要凭印象认为"应该没做"就动手改。

### 10.2 输入事件限流（dropped 计数器接入）

**现象**：`Monitor_IncDroppedEvent()` 接口存在但从未被调用，`evt_dropped` 计数器永远为 0，无法反映系统输入压力。

**排查分析**：
1. 当前架构 InputTask 既采集又处理，没有独立输入队列，所以没有"队列满丢弃"场景
2. 编码器旋转用 TIM4 硬件计数器累计，InputTask 周期性读 CNT 差值，天然限流，不会淹没系统
3. 按键事件频率低（人手按键），更不会淹没
4. 真正存在"事件被丢弃"语义的场景是 **`waking_up` 等待期间**：唤醒触发后任务要等按键全部释放才继续推进状态机，期间所有非释放事件（按键还按着、编码器还在转）都被丢弃，但这些丢弃之前没被计数

**解决方式**：在 `waking_up` 处理段接入 `Monitor_IncDroppedEvent()`：
```c
if (waking_up) {
    if (has_any_activity(&key) && !has_key_release_activity(&key))
        Monitor_IncDroppedEvent();   /* 帧间事件被抑制 */
    ...
}
```

**教训**：dropped 计数器的设计意图是"反映系统输入压力"。在没有队列的简化架构下，要找真实的"事件被丢弃"场景——`waking_up` 等待期间就是天然的丢弃点。不要为了用某个 API 而强行造场景，要从架构特性里找真实场景。

### 10.3 低功耗 Stop 模式（EXTI 唤醒 + 时钟恢复）

**现象**：原熄屏只做了"逻辑熄屏"（背光 PWM 占空比设 0），主控 MCU 仍跑在 168MHz 满速，功耗未真正降低。实施方案 B.4 要求熄屏后进 Stop 模式。

**排查分析**：
1. **唤醒源选择**：原架构靠 InputTask 20ms 轮询 key 状态检测唤醒，Stop 期间 InputTask 卡住无法轮询，必须改用 EXTI 中断唤醒
2. **可用 EXTI 唤醒源**：
   - 4 根矩阵列线 PE4/PE5/PE7/PE8（行线拉低时，任一按键按下拉低对应列线触发 EXTI 下降沿）
   - 编码器按键 PB8（ECN_SW）
3. **EXTI 中断号**：PE4 → EXTI4（独立 IRQ）；PE5/PE7/PE8 + PB8 → EXTI9_5（共享 IRQ）
4. **EXTI Handler 重复定义风险**：查 `stm32f4xx_it.c` 没有定义 EXTI4/EXTI9_5 Handler；startup 文件里这俩是 `[WEAK]` 别名，C 函数定义会覆盖汇编 [WEAK] 符号，无冲突
5. **Stop 唤醒后时钟丢失**：Stop 模式下 PLL/HSE 停，唤醒默认是 HSI 16MHz，必须调 `SystemClock_Config()` 重配 PLL 到 168MHz
6. **SystemClock_Config 声明缺失**：`main.h` 没声明 `SystemClock_Config`，跨文件调用会触发"隐式声明"警告，需在 `monitor.c` 加 `extern void SystemClock_Config(void);`
7. **IWDG 在 Stop 期间仍跑**：LSI 32KHz 是 IWDG 时钟源，Stop 期间不停，进 Stop 前必须 `HAL_IWDG_Refresh()` 喂狗，否则长 Stop 会触发复位（这其实是合理的"超长时间无操作自动复位"安全机制）
8. **FreeRTOS tick 错位**：Stop 期间 SysTick 停，唤醒后 tick 计数少算了 Stop 时长，导致 `vTaskDelay` 等定时变长。但只影响定时精度，不影响功能正确性，可接受。要彻底解决需启用 `configUSE_TICKLESS_IDLE` + 自定义 `portSUPPRESS_TICKS_AND_SLEEP`，工程量大，本次不做

**解决方式**：在 `monitor.c` 新增 `enter_stop_with_wakeup()`：
1. 配 4 行线 PE0-3 为输出低（让任一按键按下时拉低对应列线）
2. 配 4 列线 + ECN_SW 为 EXTI 下降沿
3. 配 NVIC EXTI4/EXTI9_5 优先级 5（FreeRTOS 兼容上限）
4. 清 pending flag（避免上次中断残留立即触发）
5. `HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI)` 进 Stop
6. 唤醒后 `Key_Init()` 恢复 GPIO 为扫描模式 + `SystemClock_Config()` 恢复时钟
7. `Log_Printf("[PWR] wake up from STOP")` 打印日志

`EXTI4_IRQHandler` 和 `EXTI9_5_IRQHandler` 也在 `monitor.c` 内定义，只清除 pending flag 让 `enter_stop_with_wakeup` 在 WFI 后继续执行。

调用点放在 `SYS_SCREEN_OFF` 状态的 else 分支：有按键活动→唤醒处理；无按键活动→进 Stop。

**教训**：
- Stop 模式的"任意键唤醒"看似简单，实际要解决"哪些 GPIO 配 EXTI、行线怎么拉、列线怎么检测"三层硬件问题
- EXTI IRQ Handler 的覆盖靠 [WEAK] 别名机制，要先查 `stm32f4xx_it.c` 是否已定义，避免重复定义编译错误
- Stop 唤醒后时钟默认是 HSI，不重配 PLL 整个系统会跑在 16MHz，UART/SPI 时序全错——必须 `SystemClock_Config` 恢复

### 10.4 OTA 保护（伪 OTA + Keil 工程配置踩坑）

**现象**：实施方案 B.8 要求"系统更新保护（伪 OTA 或真 OTA）"。STM32F407ZGT6 1MB Flash、无独立 bootloader、应用从 0x08000000 直接启动，真 OTA 工程量极大。

**排查分析**：
1. **真 OTA 的限制**：
   - 需要自定义 bootloader 在 Sector 0（16KB），启动时根据标志跳转到应用镜像
   - 应用镜像需双套链接地址（A 区 0x08004000 / B 区 0x08080000）
   - 链接器脚本 + 启动文件 + VTOR 重定向全套重做
   - 当前应用镜像 >200KB（FreeRTOS + GUI + FS + LCD 驱动），双 bank 布局会撑爆 1MB Flash
2. **可行方案：伪 OTA 流程闭环**
   - SD 卡专用块区放镜像头 + 数据
   - 启动时校验 magic + length + CRC32
   - 验证通过打印日志，**不实际烧写到 Flash**（避免无 bootloader 跳转后崩）
   - 清除头块防止重启循环检查

**解决方式**：
1. 新建独立模块 `ota.c/h`（按"一个文件一个功能"原则），实现 `OTA_CheckPendingUpdate()`：
   - 读 SD Block 200 头（`ota_header_t`: magic + length + crc32 + target_addr）
   - 校验 magic = "OTA1"（无镜像返回 0，不算错误）
   - 校验 length 合法（≤ 100*512 = 50KB）
   - 逐块读镜像数据，按 zlib 多项式 0xEDB88320 计算 CRC32
   - 比对 CRC，匹配则 `LogStore_Info("[OTA] update verified")` + 打印"pseudo-jump"
   - 不匹配或长度错误，`ota_clear_header()` 写零块防重启循环
2. 调用点：`InputTask` SD init 成功后、`LogStore_LoadFromSD()` 之后调 `OTA_CheckPendingUpdate()`

**踩坑：新增 .c 文件未加入 Keil 编译组**

**现象**：编译报错：
```
Error: L6218E: Undefined symbol OTA_CheckPendingUpdate (referred from monitor.o).
```

**排查分析**：
1. `monitor.c` 已 `#include "ota.h"` 且 `ota.h` 声明了 `OTA_CheckPendingUpdate`
2. `ota.c` 已实现该函数
3. 但 Keil 的 .uvprojx 没把 `ota.c` 列入编译组，所以链接器找不到 `OTA_CheckPendingUpdate` 的定义
4. STM32CubeMX 生成的 Keil 工程不会自动包含新增的 .c 文件，必须手动加入 .uvprojx

**解决方式**：直接编辑 `.uvprojx` XML，在 `log_store.c` 条目后仿照插入 `ota.c` 条目：
```xml
<File>
  <FileName>ota.c</FileName>
  <FileType>1</FileType>
  <FilePath>..\User\app\ota.c</FilePath>
</File>
```
注意路径用反斜杠 `..\User\app\ota.c`（与同组其他文件保持一致，避免跨平台大小写问题，参考 1.3 经验）。

**教训**：
- 新增 .c 文件后必须同步改 `.uvprojx`，否则即使代码正确也无法编译通过
- Keil 会缓存 .uvprojx，必须**先关闭 Keil → 重新打开**才能加载新增的源文件，直接 Rebuild 看不到新文件
- 路径写法要与同组其他条目保持一致（反斜杠 vs 正斜杠），避免触发 1.3 提到的跨平台问题
- OTA 的"伪"是有意识的工程权衡：在没有 bootloader 的情况下硬做"真 OTA"会破坏系统稳定性。先做流程闭环，未来加 bootloader 时再补 HAL_FLASH_Program 烧写和 VTOR 跳转

## 九、总结

### 9.1 主要经验

| 类别 | 核心教训 |
|------|----------|
| 编译构建 | HAL 模块需手动启用宏 + 添加源文件；跨平台注意路径大小写 |
| 任务调度 | 心跳必须覆盖所有执行路径；`portMAX_DELAY` 在带看门狗系统中是危险信号 |
| 硬件时序 | 调度器启动前的代码不能有长阻塞；外部硬件初始化放到任务中 |
| UI 交互 | 按键冲突用长/短按区分；无操作不打扰用户 |
| 存储一致性 | 非易失性存储必须加 CRC 校验防掉电损坏 |
| 硬件排障 | 从软件到硬件逐层排查，先确认信号再查接线 |

### 9.2 关键设计决策

1. **FreeRTOS 堆大小 48KB**：兼顾任务栈和动态分配需求，太小会触发 `ERR:HP`
2. **IWDG 超时 12.5 秒**：足够长以容忍偶发阻塞，又能及时发现真卡死
3. **心跳检测周期 5 秒**：是 IWDG 超时的 1/2.5，留出喂狗余量
4. **任务栏只在桌面显示**：避免改动所有应用的布局
5. **音乐后台播放**：MusicTask 独立于 UI 任务，最小化不影响播放
